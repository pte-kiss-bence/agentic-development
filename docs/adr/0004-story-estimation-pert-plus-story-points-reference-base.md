# pte-openspec: stories carry a PERT + Story-Points estimate as an AI-authored reference base

The lean story-card schema deliberately dropped the old *Becslés* section (see the schema in `pte-openspec-to-stories`). We are **reintroducing** it as a visible `## Estimation` section, because estimation turns out to be a load-bearing part of how PTE operates: the AI estimate is the **authoritative reference base** the team relies on, and managers layer their own internal- and client-facing **multipliers** on top of it downstream. So the reversal is intentional, not sediment.

## What we decided

- **Two coupled views, one source.** Each story is estimated with **PERT three-point** in **ideal engineer-hours** (`O`/`M`/`P` → `Eβ = (O+4M+P)/6`, `σ = (P−O)/6`), and a modified-**Fibonacci Story Point** is **derived deterministically from `Eβ`** by a fixed table (6 ideal engineer-hours = 1 ideal day). The SP is never guessed independently, so the two views cannot contradict. The math lives once in `pte-openspec-shared/CONVENTIONS.md`.
- **O/M/P come from a weighted complexity rubric, not a cold guess.** A fixed factor set scored from the card + spec drives the estimate: **M-drivers** (behaviour volume, business-logic complexity, integration/coupling, interface surface, data/persistence, test/QA effort, deploy/infra) weighted into `M = round(S·k)`, optional **modifiers** (security, compliance/audit, perf, i18n, migration, observability, docs) that only tax stories that hit them, and separate **σ-drivers** (requirement clarity, tech novelty, domain novelty, dependency stability) that set the O↔P spread so uncertainty is honest and can itself trip the split-warning. The weights, `k`, and spread coefficients are the org's tuning knobs, co-located with the formula.
- **Reference base only; multipliers are out of scope.** The skills emit the raw base (hours + SP). The internal/client multipliers are a human manager judgement applied off-pipeline (quotes/spreadsheets), and are never computed, stored, or synced by the skills — so no client-facing number leaks through Jira.
- **Split-warning is flag-only.** `SP ≥ 13` or `σ/Eβ > 0.25` prints a `⚠` split-candidate note but still ships the card. INVEST stays the qualitative gate; the estimate only surfaces an objective signal, it does not auto-split. (The σ threshold was originally 0.5 — recalibrated to 0.25 because the σ-driver spread coefficients cap `σ/Eβ` at ~0.32, so 0.5 was unreachable and the uncertainty branch was dead; 0.25 trips at `u > 0.75`, genuine spike territory.)
- **Story points is now local-owned.** This **flips** `pte-openspec-jira-sync`'s field-ownership: the SP flows **Local → Jira** into the structured *Story points* field, superseding the previous "estimate is Jira-owned, pulled into the card" rule. The PERT base lives in the card's pipeline-only fence (stripped from the pushed Description); two numbers map to structured fields — the SP to *Story points*, the `Eβ` hours to *Original estimate*.
- **Epic estimate is a rollup, gated on completeness.** `pte-openspec-to-epics` sums its child stories' `Eβ` and SP — but only once **every** child is estimated; otherwise the section is marked `⚠ nem minden story esztimált` rather than guessing. Since stories are estimated *after* epics are minted, the rollup is a separate pass over the epic (diff-don't-clobber).

## Considered options

- **Abstract story points as the PERT unit** — rejected: multipliers on story points have no time/cost meaning, which defeats the reference-base use.
- **T-shirt sizes** — rejected at story level (kept as a possible future epic-level lens): coarser and still needs a further map to points for Jira velocity. Modified Fibonacci maps 1:1 to Jira's *Story points* field.
- **Hard split-gate on size** — rejected: an AI estimate is noisy; a hard numeric gate would over-split. Flag-and-let-the-human-decide fits better.
- **Keep estimate Jira-owned / hidden pipeline-only** — rejected: the team treats the AI number as authoritative and needs it visible and in Jira's structured field, so ownership flips to local.
- **Reference-class forecasting (anchor stories with known actual hours)** — rejected as the *basis* for now: more empirically accurate but needs a calibrated set of historical actuals PTE does not yet have, and it is opaque. A **parametric weighted-factor rubric** was chosen instead — transparent, tunable, works day one; a reference-class anchor can be layered on later as actuals accrue without changing the schema.
